# CAN-003 (API) — Canvas image assets

Objective: backend half of CAN-003 — validated image upload, stable managed storage, serving the bytes back, and asset information in the canvas export. Drag-drop, clipboard and PNG/SVG rendering wait for the frontend, where Excalidraw produces them.
Branch: `feat/can-003-assets-api` (stacked on `feat/can-002-canvases-api`) · Delivery: `ask-on-risk` · Test runner: Vitest (`pnpm test`, `pnpm test:e2e` in `apps/api`; `pnpm test` in `packages/contracts`).

## Specs

- **S1** — CAN-003: "adjuntar/arrastrar/pegar imágenes, validar tipo y tamaño, almacenamiento estable y exportación PNG/SVG."
- **S2** — Acceptance: "imágenes sobreviven reinicio/backup; sin rutas temporales; validación y protección path traversal; exportación conserva recursos."
- **S3** — Tests: "PNG/JPEG/WebP soportados, inválidos, pesados, drag-drop, portapapeles, restore."
- **S4** — Plan §7 route: "`POST /canvases/:id/assets`".
- **S5** — Plan §4.4 and §6: "Imágenes/adjuntos en directorio administrado y referencias estables, no rutas temporales." · "Validar tamaños, tipos MIME y rutas de archivos; impedir path traversal." · "No almacenar imágenes grandes embebidas en JSON de escenas."

Out of scope: drag-drop, clipboard and PNG/SVG rendering (frontend; Excalidraw renders on the client); backup and restore of the assets directory (SYS); thumbnails (CAN-004); deleting unreferenced assets.

Assumptions (decided here, not in the plan):
- A1: Accepted types are exactly PNG, JPEG and WebP. SVG is rejected because it can carry scripts. The type comes from the file's bytes; the client's declared type and extension are ignored. Anything else → 415 `Unsupported image type`.
- A2: `POST /canvases/:id/assets` takes multipart field `file`, at most 10 MB (→ 413), no text fields (→ 400), and answers 201 `{ id, filename, mimeType, sizeBytes, checksum, createdAt }`. Missing file → 400. Unknown canvas → 404. Archived canvases accept uploads, as they accept saves, so an open tab cannot lose work.
- A3: Upload does not create a `canvas_assets` row: that table stays derived from `scene.files` (CAN-002 A2). An uploaded asset that no scene references stays stored; nothing deletes it yet.
- A4: `GET /assets/:id/content` (not in §7) returns the bytes so the client can render them, with the stored type, `nosniff`, a sandbox CSP and immutable caching.
- A5: Files live under `ASSETS_DIR`, which must be absolute; the default is `~/.mimir/assets`. Storage keys are generated by the server (`<uuid>.<ext>`) and never come from client input. The client's filename is metadata only.
- A6: Writes go to a temporary file inside the managed directory, are flushed, then renamed, and only then is the row inserted. A crash can leave an unreferenced file but never a row without a file.
- A7: The editable export keeps its scene and adds `assets`, a manifest of what the scene references. The bytes stay out of the file, so it restores fully only on an instance that holds those assets; moving between machines is the backup's job (SYS). PNG/SVG exports contain the images because the client renders them from `GET /assets/:id/content`.
- A8: A `dataURL` key holding a `data:` string anywhere in a scene is rejected with the existing embedded-image message, closing the CAN-002 advisory about `elements` and `appState`.
